# Карточка merge request текущей ветки (GitLab)

Дата: 11.11.2026. Статус: черновик на согласование.

## Зачем

Ветки исправлений называются `fix/...`, merge request по ним заводят вручную в
веб-интерфейсе корпоративного GitLab. Раздражает не объем работы, а переключение
контекста: уйти из EDT в браузер, вспомнить проект, выбрать ветки, заполнить
заголовок. Дальше MR живет своей жизнью — ревью, апрувы, Sonar и прочие проверки,
затем слияние, — и узнать, что с ним происходит, тоже можно только в браузере.

Задача: MR текущей ветки создается и показывается в панели Git Flow, а браузер
нужен только для содержательной работы с ним (комментарии, код-ревью).

Это продолжение темы «Связь ветки с Merge Request» из
[обзора Git-клиентов](../../git-clients-overview.md).

## Цели

- Создать MR для текущей ветки из панели: одна кнопка, разумные значения по
  умолчанию, ничего обязательного сверх заголовка.
- Показать состояние MR этой ветки: открыт, черновик, апрувы, пайплайн,
  конфликты, обсуждения.
- Один клик до страницы MR в браузере.
- Настройка подключения в одном месте: адрес, токен, сертификат, проверка
  подключения одной кнопкой.

## Не-цели (в этой итерации)

- Список всех MR проекта или «мои MR».
- Одобрение MR, комментарии, ревью из EDT.
- Слияние MR из EDT — обсуждается отдельно, следующим шагом.
- Таймер и фоновое обновление по расписанию.
- GitHub и GitLab.com как отдельные сценарии.
- Напоминания. Нет токена — нет строки, панель молчит.

## Проверенные факты

- EDT 2026.1.3 установлена здесь: `C:\Program Files (x86)\1C\1CE\components\`
  `1c-edt-2026.1.3+25-x86_64\plugins` (1527 бандлов), EGit 6.8.12 — совпадает
  с target-файлом. JVM EDT — `axiom-jdk-full 17.0.16`.
- `org.eclipse.equinox.security` 1.4.100 и фрагмент `win32.x86_64` в EDT есть:
  шифрованное хранилище доступно.
- `akeso.dept07` = 10.71.0.153. Сертификат `CN=akeso.dept07` выдан
  `CN=Kenobi-SubCA`, корень `CN=Yoda-RootCA`.
- Рукопожатие проверено кодом на JVM самой EDT: `KeyStore.getInstance("Windows-ROOT",

  проходит с полной проверкой цепочки. То есть на Windows настройка сертификата
  действительно не нужна — это проверено, а не предположено.
- В Windows включен прокси `telstar.dept07:8080`, но прямое подключение к
  `akeso.dept07` работает. Прокси не нужен; если появится, включаем отдельно.
- Реальные remote у репозиториев этой сети: `https://akeso.dept07/BP/<...>.git`,
  `https://akeso.dept07/BP/Extensions/<...>.git`, без порта, без префикса
  экземпляра. Есть также `http://helius/...` — другой сервер, и репозитории
  GitHub. Значит путь проекта из remote выводится, но хост надо проверять.
- MR по умолчанию создаются в `master`.

Инструменты:

- Java 17 (Zulu 17.0.14), Git 2.45, Maven 3.9.16 в `.tools` (обертки
  `.tools/bin/mvn` и `.tools/bin/mvn.cmd`), локальный `.m2` есть.
- В target-платформе есть `com.google.gson 2.10.1`, `jackson-core/databind 2.12.1`.
- `mvn verify` компилирует core и UI, но тесты на Windows не проходят:
  14 падений из-за CRLF (глобальный `core.autocrlf=true`), 3 ошибки из-за
  запрета записи в `%TEMP%` (корпоративный EDR), остальное — кодировка при
  `platform encoding: Cp1251`. Тесты писались на macOS и требуют починки под
  Windows до того, как на них можно опираться.

## Пользовательский сценарий

1. Работа в ветке `fix/12345-описание`, изменения отправлены в `origin`.
2. Под строкой ветки появилась строка MR: `MR не создан · Создать`.
3. «Создать» открывает диалог: заголовок заполнен первой строкой последнего
   коммита, целевая ветка `default_branch` проекта (`master`), галочки
   «Черновик» и «Удалить ветку после слияния».
4. После создания строка показывает `!123 · Ревью 0/2 · Пайплайн идет`.
5. Кнопка обновления рядом с веткой обновляет и MR. Клик по строке открывает
   страницу MR в браузере.

## Правило безопасности

Токен отправляется только на хост из настроек. Если remote репозитория указывает
на другой хост (`github.com`, `helius`), строка MR не появляется и ни один
запрос не уходит. Настройки хранятся вместе с хостом сервера, а не глобально
«на все репозитории»: токен относится к конкретному GitLab.

## Настройки

Отдельная форма, открывается из шестеренки панели пунктом **GitLab…** (меню
настроек создается в `BranchPicker`). Пункт виден всегда.

| Поле | Поведение |
| --- | --- |
| Адрес сервера | Подставляется из `remote.origin.url`. Можно изменить; пустое значение означает «брать из remote». |
| Токен | Поле с сокрытием ввода. Ссылка «Создать токен» открывает страницу personal access tokens этого сервера. |
| Сертификат | Переключатель «Доверять сертификатам Windows» (по умолчанию) или «Файл сертификата…». |
| Проверить подключение | `GET /api/v4/user` плюс `GET /api/v4/personal_access_tokens/self` с текущими значениями; результат словами. |
| Сохранить / Отмена | Обычные кнопки. |

Проверка подключения отвечает словами: «Подключено как Иванов Иван», «Токен не
принят», «Токен без права записи: нужен scope api», «Сертификат сервера не
доверен», «Сервер не отвечает». Это снимает главный риск настройки — непонятно,
что именно не так.

Хранение:

- обычные значения — узел `dev.edt.gitflow.ui/gitlab` в `InstanceScope`
  (`baseUrl`, `serverHost`, `certMode`, `certFile`);
- токен — шифрованное хранилище Eclipse (`SecurePreferencesFactory`), ключ
  `gitlab.token.<host>`;
- открытым текстом токен не сохраняется нигде. Если шифрованное хранилище
  недоступно, форма сообщает об ошибке и токен не сохраняет.

## Что видно в панели

Строка MR — новый `Composite` в один ряд под строкой ветки (после `header` с
`branchButton` и `syncButton`). Показывается только MR текущей ветки. Состав
строки — предмет отдельного согласования; минимальный вариант:

| Состояние | Что в строке |
| --- | --- |
| Токена нет или чужой хост | строки нет |
| Ветка по умолчанию (`master`) | строки нет |
| Detached HEAD | строки нет |
| Ветка не отправлена | `Ветка не отправлена` без кнопки `Создать` — см. открытые вопросы |
| MR нет | `MR не создан` · кнопка `Создать` |
| Открыт, черновик | `!123 · Черновик` |
| Открыт, нужны апрувы | `!123 · Одобрено 1 из 2` |
| Пайплайн | `Сборка идет` / `Сборка прошла` / `Сборка упала` |
| Конфликты | `Есть конфликты` |
| Обсуждения | `Есть незакрытые обсуждения` |
| Слит | `!123 · Слит` |
| Нет связи | последнее известное состояние и пометка `нет связи` |

Правила: если по ветке нашлось несколько MR, берем открытый, иначе самый
свежий по `updated_at`. Кнопки строки: `Создать` (когда MR нет), клик по тексту
открывает MR, контекстное меню — `Открыть в браузере`, `Скопировать ссылку`.

Обновление: по кнопке синхронизации рядом с веткой, при показе панели и после
успешной отправки в `origin`. Таймера нет.

## Как устроено

### Core (`dev.edt.gitflow.core`)

Core остается без SWT и Eclipse UI, чтобы тесты шли как обычный JUnit.

- `GitLabRemote` — разбор `remote.origin.url`: схема, хост, порт, путь проекта,
  база API (`/api/v4`). Логика разбора переиспользуется из `GitLinks`
  (`baseUrl` сейчас приватный — вынести в общий класс).
- `GitLabClient` — HTTP-клиент на `java.net.http.HttpClient` с готовым
  `SSLContext`. Методы: `currentUser()`, `tokenScopes()`, `project()`,
  `findMergeRequest(branch)`, `mergeRequest(iid)`, `approvals(iid)`,
  `createMergeRequest(...)`.
- `MergeRequestInfo` — неизменяемый снимок: `iid`, `title`, `state`, `draft`,
  `webUrl`, `approvedCount`, `approvalsRequired`, `pipelineStatus`,
  `hasConflicts`, `discussionsResolved`, `notesCount`, `mergeStatus`.
- `GitLabException` — тип ошибки: `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`,
  `NETWORK`, `TLS`, `SERVER`.

Запросы:

| Что | Запрос |
| --- | --- |
| Проверка подключения | `GET /api/v4/user`, `GET /api/v4/personal_access_tokens/self` |
| Проект (кэш в памяти) | `GET /api/v4/projects/{path}` |
| MR по ветке | `GET /api/v4/projects/{path}/merge_requests?source_branch={branch}&state=all&order_by=updated_at&per_page=5` |
| Детали MR | `GET /api/v4/projects/{path}/merge_requests/{iid}` |
| Апрувы | `GET /api/v4/projects/{path}/merge_requests/{iid}/approvals` |
| Создание | `POST /api/v4/projects/{path}/merge_requests` |

Авторизация — заголовок `PRIVATE-TOKEN`. Токену нужен scope `api`: `read_api`
не позволит создать MR.

Разбор JSON — через Gson, который уже есть в target-платформе; в манифест core
добавляется `Import-Package: com.google.gson` с `resolution:=optional`, чтобы
core оставался запускаемым в тестах без EGit. Ручной разбор не пишем.

### Совместимость с версиями GitLab

Версия и редакция сервера заранее не известны, поэтому клиент не полагается на
них и деградирует молча:

- `detailed_merge_status` отсутствует — используем `merge_status` и
  `has_conflicts`;
- `draft` отсутствует — черновик определяется по префиксу `Draft:`/`WIP:` в
  заголовке;
- `approvals` отвечает 403 или 404 (редакция без правил апрувов) — счетчик
  апрувов не показывается, остальное работает;
- `head_pipeline` пуст — статус сборки не показывается.

### UI (`dev.edt.gitflow.ui`)

- `GitLabSettingsDialog` — форма настроек.
- `MergeRequestPane` — строка MR: `Composite` плюс метка состояния и кнопки.
- `MergeRequestRefreshJob` — `Job`, не блокирующий UI; результат отдается в
  `Display.asyncExec`. Одновременно выполняется только одно обновление.
- `MergeRequestCreateDialog` — диалог создания.
- `GitLabSettings` — чтение и запись настроек, доступ к шифрованному хранилищу.
- Новые ключи в `Messages` для русского и английского.

Контракт `MergeRequestPane`: `setRepository`, `setBranch`, `clear`,
`showSnapshot`, `showError`. Кеш снимка живет в панели и сбрасывается при смене
репозитория, ветки или `HEAD`.

В `MANIFEST.MF` UI-бандла добавляется `org.eclipse.equinox.security`.
`java.net.http` — часть JDK, импорт в манифесте не нужен.

### Сеть и сертификаты

`SSLContext` строится один раз на настройки:

1. «Доверять сертификатам Windows» — `KeyStore.getInstance("Windows-ROOT",
   "SunMSCAPI")` как источник доверия; проверено на JVM EDT.
2. «Файл сертификата» — чтение PEM/X.509 через `CertificateFactory`, `KeyStore`
   в памяти, `TrustManagerFactory`. Вариант для macOS и для сертификата файлом.

Галочки «не проверять сертификат» не будет.

Таймауты: соединение 5 с, запрос 10 с. Запросы идут только при открытой панели и
только при наличии токена.

### Ошибки

| Ситуация | Поведение |
| --- | --- |
| Нет токена | строки MR нет |
| 400 при создании | `Ветка не отправлена на сервер` |
| 409 при создании | `MR уже создан`, затем обновление строки |
| 401 | `Токен не принят`, пункт `Настроить GitLab…` |
| 403 | `Недостаточно прав: нужен scope api` |
| 404 проекта или MR | строка как «MR не создан» |
| Нет сети, таймаут | последнее известное состояние с пометкой `нет связи` |
| Ошибка TLS | `Сертификат сервера не доверен`, пункт `Настроить GitLab…` |
| 429 | повтор не раньше следующего обновления, без диалогов |

Диалоги ошибок не открываются: сообщение уходит в существующую строку статуса
`GitFlowView.publish`.

## Тесты

Core тестируется на фейковом сервере: `com.sun.net.httpserver.HttpServer` из JDK
на случайном порту. Проверяется:

- разбор `remote.origin.url`: `https`, `ssh://`, `git@host:path`, вложенные
  группы, `.git` на конце, чужой хост;
- успешное чтение MR, включая пустой `head_pipeline`, нулевые апрувы и
  отсутствие `approvals`;
- коды 401, 403, 404, 409, 500 и таймаут;
- создание MR: тело запроса, черновик через префикс `Draft:`,
  `remove_source_branch`;
- падение запроса на чужой хост запрещено правилом безопасности.

UI проверяется без открытия окон: форматирование строки состояния и наличие
новых ключей в русских и английских ресурсах.

До начала работы над карточкой нужно починить три вещи, из-за которых тесты
падают на Windows: CRLF в ожиданиях, кодировку при тестах и запись в `%TEMP%`.
Иначе непонятно, что сломала новая функция, а что было раньше.

Ручная проверка в EDT обязательна: панель, форма настроек, создание MR на
тестовой ветке.

## Сборка

Maven развернут в `.tools`. `releng/edt-2026-1.target` указывает на macOS-путь;
для локальной сборки путь подменяется на каталог `plugins` установленной EDT и
не коммитится.

## Открытые вопросы

- Что показывать для ветки, которой нет на сервере: `Ветка не отправлена` без
  кнопки или пустоту.
- Точный состав строки MR сверх минимального набора.
- Нужен ли в диалоге создания выбор целевой ветки, или всегда `default_branch`.
- Поведение после слияния, пока ветка не удалена.
