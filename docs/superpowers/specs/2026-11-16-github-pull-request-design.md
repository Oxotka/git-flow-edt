# Карточка pull request текущей ветки (GitHub)

Дата: 16.11.2026. Статус: черновик на согласование.

## Зачем

Карточка merge request для GitLab уже есть: она показывает состояние
запроса по текущей ветке и позволяет создать его из панели. В рабочей области
встречаются и репозитории GitHub. Для них плагин умеет только открывать ссылки
на файл, ветку и коммит, а pull request приходится искать в браузере.

Задача: тот же сценарий, что у GitLab, но для GitHub. Ветка `fix/...` уже
отправлена, в панели видно состояние PR и кнопку создания; браузер нужен только
для содержательной работы с запросом.

## Цели

- Создать pull request текущей ветки из панели: заголовок из последнего коммита,
  целевая ветка по умолчанию, черновик, проверяющий.
- Показать состояние PR: открыт, черновик, проверки, одобрения, конфликты,
  готовность к слиянию, кем и когда слит.
- Один клик до страницы PR в браузере.
- Настройка подключения в одном месте: адрес, тип хостинга, токен, сертификат,
  проверка подключения.
- Не менять поведение GitLab: существующий путь и его тесты остаются рабочими.

## Не-цели (в этой итерации)

- Список всех PR проекта или «мои PR».
- Одобрение, комментарии, ревью и слияние PR из EDT.
- Незакрытые обсуждения (review threads): REST API GitHub их не отдает, нужен
  GraphQL. В первой итерации строка их не показывает.
- PR из fork-веток и чужих репозиториев.
- Переоткрытие закрытого PR из панели.
- GitHub.com отдельно от GitHub Enterprise: поддерживаются оба, различие только
  в адресе API.
- OAuth и device flow: только личный токен.
- Уведомления и обновление по таймеру.

## Пользовательский сценарий

1. Работа в ветке `fix/12345-описание`, изменения отправлены в `origin`.
2. Под строкой ветки появилась строка PR: `PR не создан · Создать`.
3. «Создать» открывает диалог: заголовок из первой строки последнего коммита,
   целевая ветка — ветка по умолчанию проекта (`main` или `master`), поля
   описания, черновик и проверяющий.
4. После создания строка показывает `PR-123 · Проверки идут`.
5. Синхронизация рядом с веткой обновляет и PR. Клик по строке открывает PR
   в браузере.

## Правило безопасности

Токен отправляется только на хост из настроек. Если remote репозитория указывает
на другой хост, строка PR не появляется и запросы не уходят. Настройки хранятся
для каждого хоста отдельно: в рабочей области могут быть и корпоративный GitLab,
и GitHub.

Запросы панели всегда идут на хост из `remote.origin.url`: сохраненный адрес
сервера не перенаправляет их и не меняет ключ токена. Адрес в форме — значение
по умолчанию и справочная информация. Проверка подключения в форме использует
введенный адрес, потому что это явное действие пользователя: он сам указывает,
куда проверить токен.

Если пользователь отредактировал адрес в форме на другой хост, панель все равно
не начнет ходить на него: для этого хост должен совпасть с remote репозитория.

## Модель хостинга

Провайдер определяется по хосту `remote.origin.url`:

| Хост | Провайдер |
| --- | --- |
| `github.com`, хост содержит `github` | GitHub |
| хост содержит `gitlab` | GitLab |
| иначе | сохраненный выбор для хоста, иначе GitLab |

Правило «иначе — GitLab» сохраняет текущее поведение для корпоративных
GitLab-серверов с произвольным доменом. Для GitHub Enterprise с доменом без
слова `github` тип выбирается вручную в форме настроек и запоминается для хоста.

Фабрика в UI (`HostingConnection`) по remote и настройкам возвращает готовый
`MergeRequestProvider` или `null`, если хостинг не настроен. Панель и диалог
создания не знают, GitLab это или GitHub.

## Настройки

Пункт в шестеренке панели называется **Хостинг…** и открывает одну форму для
любого провайдера. Хост и провайдер определяются по выбранному репозиторию.

| Поле | Поведение |
| --- | --- |
| Адрес сервера | Корень сервера из remote. Можно изменить для проверки и сохранения как значение по умолчанию; запросы панели от этого адреса не зависят. |
| Тип сервера | GitLab или GitHub. По умолчанию по правилу выше; доступен для GitHub Enterprise с нестандартным доменом. |
| Токен | Поле с сокрытием ввода; ссылка на страницу выпуска токена у выбранного провайдера. |
| Сертификат | «Доверять сертификатам Windows» (по умолчанию) или файл сертификата. |
| Ветки для запроса | Префиксы через запятую; по умолчанию `fix/`, `feat/`. Общая настройка для обоих провайдеров. |
| Проверить подключение | Текущий пользователь, право на создание запроса (справочно), доступ к участникам. Результат словами; для GitHub перечисляются нужные права токена. |
| Сохранить / Отмена | Обычные кнопки. |

Хранение:

- `hosting` в `InstanceScope`: `certMode`, `certFile`, `branchPrefixes`,
  `baseUrl.<host>`, `provider.<host>`; адрес хранится для формы и не участвует
  в запросах;
- токен — в шифрованном хранилище Eclipse, ключ `hosting.token.<host>`;
- открытым текстом токен не сохраняется. Если шифрованное хранилище недоступно,
  форма сообщает об ошибке и токен не сохраняет.

Совместимость с сохраненными настройками: при чтении новых ключей нет —
используются старые `gitlab` (`serverHost`, `baseUrl`, `certMode`, `certFile`,
`branchPrefixes`) и токен `gitlab.token.<host>`, кеш проверяющих
`gitlab/reviewers.<project>`. Старые ключи не удаляются: миграция только на
чтение. При первом сохранении пишутся новые ключи.

## Что видно в панели

Строка PR — тот же `Composite` под строкой ветки, что и у GitLab.

| Состояние | Что в строке |
| --- | --- |
| Токена нет или чужой хост | строки нет |
| Ветка по умолчанию | строки нет |
| Detached HEAD | строки нет |
| Ветка не отправлена | `Ветка не отправлена` без кнопки `Создать` |
| PR нет | `PR не создан` · ссылка `Создать` |
| Открыт, черновик | `PR-123 · Черновик` |
| Открыт, есть одобрения | `PR-123 · Одобрено 1 из 2` или `PR-123 · Одобрено 1`, если правило не известно |
| Проверки | `Проверки идут` / `Проверки прошли` / `Проверки упали` |
| Конфликты | `Есть конфликты` |
| Готов к слиянию | `Готов к слиянию` |
| Закрыт без слияния | `PR-123 · Закрыт`, без ссылки `Создать` |
| Слит | `PR-123 · Слит · кто · когда` |

Правила:

- если по ветке нашлось несколько PR, берется открытый, иначе самый свежий по
  времени обновления;
- номер в строке — `PR-123` (у GitLab `MR-123`);
- закрытый PR показывается как `Закрыт`; для повторного создания нужно открыть
  его в браузере;
- обновление: по кнопке синхронизации, при показе панели и после успешной
  отправки ветки;
- текст строки собирается из состояния, которое вернул провайдер; форматирование
  общее для обоих провайдеров.

## Как устроено

### Core (`dev.edt.gitflow.core`)

Core остается без SWT и Eclipse UI.

- `HostingException` заменяет `GitLabException` (переименование, поведение
  прежнее). Виды: `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`,
  `BAD_REQUEST`, `NETWORK`, `TLS`, `SERVER`, `RATE_LIMIT`.
- `MergeRequestProvider` дополняется общими операциями:
  `currentUser()`, `defaultBranch()`, `canCreateRequests()`, `requestShortName()`
  (`MR` или `PR`), `requestFullName()` (`merge request` или `pull request`),
  `supportsDeleteSourceBranch()`. `canCreateRequests()` — справочный: строка и
  диалог опираются на фактический ответ API, а не на него.
- `GitHubRemote` — разбор `remote.origin.url`: хост, адрес сайта, `owner/repo`,
  база API. Для `github.com` — `https://api.github.com`, для остальных хостов —
  `https://<host>/api/v3` (GitHub Enterprise Server). Сохраненный адрес сервера
  в разборе не участвует.
- `GitHubClient implements MergeRequestProvider` — HTTP-клиент на
  `java.net.http.HttpClient` с заголовком `Authorization: Bearer`, с готовым
  `SSLContext` и теми же таймаутами, что у GitLab.
- `CreateMergeRequest` перестает знать про JSON: хранит общие поля
  (`sourceBranch`, `targetBranch`, `title`, `description`, `draft`,
  `reviewer`, `removeSourceBranch`), тело запроса собирает каждый клиент.
  Проверяющий хранится как `ProjectMember`: GitLab использует `id`, GitHub —
  `username` (логин).
- `MergeRequestStatus` пополняется флагом `approvalsRequiredKnown`, чтобы
  отличать «правило требует 0» от «правило неизвестно». Остальные поля общие.

Состояние PR приводится к терминам строки: `opened`, `merged`, `closed`.
Проверки приводятся к `success` / `failed` / `running`, как у GitLab.

### Запросы GitHub

| Что | Запрос |
| --- | --- |
| Проверка подключения | `GET /user`, `GET /repos/{owner}/{repo}` |
| PR по ветке | `GET /repos/{o}/{r}/pulls?head={o}:{branch}&state=all&sort=updated&direction=desc&per_page=10` |
| Детали PR | `GET /repos/{o}/{r}/pulls/{number}` |
| Проверки | `GET /repos/{o}/{r}/commits/{sha}/check-runs?per_page=100`; если проверок нет — `GET /repos/{o}/{r}/commits/{sha}/status` |
| Ревью | `GET /repos/{o}/{r}/pulls/{number}/reviews?per_page=100` |
| Требуемые одобрения | `GET /repos/{o}/{r}/branches/{base}/protection/required_pull_request_reviews` |
| Участники | `GET /repos/{o}/{r}/collaborators?per_page=100` |
| Создание | `POST /repos/{o}/{r}/pulls` |
| Назначить проверяющего | `POST /repos/{o}/{r}/pulls/{number}/requested_reviewers` |

Заголовки: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version:
2022-11-28`, `Authorization: Bearer`. Тело создания PR:
`{title, head: "<owner>:<branch>", base, body, draft}`.

Одобрения считаются по решающим ревью: последнее ревью каждого пользователя
с состоянием `APPROVED`, `CHANGES_REQUESTED` или `DISMISSED`. `APPROVED` —
одобрение; `CHANGES_REQUESTED` и `DISMISSED` снимают его; `COMMENTED` и
`PENDING` не меняют. Устаревшие одобрения после новых коммитов GitHub снимает
сам — они приходят как `DISMISSED`.

Обязательное число одобрений — из branch protection; endpoint может ответить 403
или 404, тогда правило неизвестно и показывается только число одобрений.

`mergeable` и `mergeable_state` в деталях PR: `false` или `dirty` — конфликты,
`clean` — готов к слиянию. Пока GitHub считает слияние, `mergeable` пуст:
конфликты и готовность не показываются до следующего обновления. Повторный
запрос сразу после создания не делается: строка обновится по кнопке
синхронизации или при следующем показе панели.

Проверяющий назначается отдельным запросом после создания PR. Если он не
удался (422, 403, 404), PR уже создан: ошибка пишется в журнал, а строка
показывает созданный PR. Назначить проверяющего можно в браузере.

### Проверки

Итог по check-runs: проверки считаются упавшими, если есть завершенная проверка
с выводом `failure`, `timed_out`, `cancelled`, `action_required` или
`startup_failure`; идущими — если упавших нет и есть проверка не в состоянии
`completed`; прошедшими — если все завершены с `success`, `neutral`, `skipped`
или `stale`. Приоритет: упали, затем идут, затем прошли.

Если check-runs нет, используется combined status: `failure` и `error` — упали,
`pending` — идут, `success` — прошли. Если нет ни того, ни другого, статус
проверок не показывается.

### Совместимость и деградация

- Check-runs недоступны (403/404) — статус проверок не показывается.
- Branch protection недоступен — показывается только число одобрений.
- `mergeable` пуст — не показываются конфликты и готовность.
- Collaborators недоступны (403) — список проверяющих пуст; проверяющего можно
  ввести логином.
- Токен fine-grained: REST не отдает набор прав токена. Нужны `Pull requests:
  read and write`, `Contents: read`, `Metadata: read`; для проверок —
  `Checks: read`, для правила одобрений — `Administration: read` (последние два
  необязательны: без них карточка просто беднее). Проверка подключения
  перечисляет эти права; право на создание PR показывается справочно по
  `permissions.push`, а фактическая попытка создания может ответить 403 —
  тогда строка статуса говорит, чего не хватает.
- Черновик: флаг `draft` при создании не поддерживается только для fork-PR,
  которые в итерацию не входят.

### UI (`dev.edt.gitflow.ui`)

- `GitLabSettings` → `HostingSettings`, `GitLabSettingsDialog` →
  `HostingSettingsDialog`, `GitLabSsl` → `HostingSsl`, `GitLabLog` →
  `HostingLog`. Старые настройки читаются как fallback.
- `HostingConnection` — выбор провайдера по remote, создание клиента и контекста
  сертификатов в фоновой задаче. Токен берется только для хоста remote и только
  если сохраненный хост с ним совпадает.
- `MergeRequestPane` создает клиента через `HostingConnection`, а не
  `new GitLabClient(...)`. Поведение обновления, кеш ключа «репозиторий|ветка» и
  фильтр веток сохраняются. Ветка по умолчанию берется у провайдера.
- `MergeRequestCreateDialog` работает через интерфейс: целевые ветки, заголовок,
  описание, черновик. Для GitHub скрывается «Удалить ветку после слияния»
  (GitHub не удаляет ветку по PR, это настройка репозитория), проверяющий
  выбирается из collaborators или вводится логином; после создания назначается
  запросом `requested_reviewers`.
- `MergeRequestText` получает короткое и полное имя запроса от провайдера:
  `MR-123` / `PR-123`, «Создать MR» / «Создать PR», «Новый merge request» /
  «Новый pull request». Строки параметризуются в `messages*.properties`.
- Новые ключи добавляются и в русские, и в английские ресурсы.
  `MetadataTypeTest` и `UiClassLoadingTest` не должны ломаться.

### Сеть и сертификаты

Соединение 5 с, запрос 10 с, `SSLContext` из системного хранилища Windows или
из файла сертификата. Для GitHub Enterprise сертификат корпоративного CA
настраивается так же.

GitHub ходит через системный прокси (стандартный `ProxySelector` JVM): из
корпоративной сети `github.com` обычно доступен только через него. Прокси видит
только хост назначения, токен находится внутри TLS. GitLab, как и раньше, ходит
напрямую: для корпоративного сервера это проверено.

### Ошибки

| Ситуация | Поведение |
| --- | --- |
| Нет токена | строки PR нет |
| 401 | `Токен не принят`, пункт `Настроить хостинг…` |
| 403 без права на запись | `Нет права на создание PR` |
| 403/429 лимита запросов | `Лимит запросов GitHub исчерпан`; повторяется при следующем обновлении |
| 404 репозитория или PR | строка как «PR не создан» |
| 422 при создании, ветка не отправлена | `Ветка не отправлена на сервер` |
| 422 при создании, PR уже есть | `PR уже создан`, затем обновление строки |
| Закрытый PR | `PR-123 · Закрыт`, без кнопки `Создать` |
| Проверяющий не назначен | PR создан, запись в журнал; назначить можно в браузере |
| Нет сети, таймаут | последнее известное состояние с пометкой `нет связи` |
| Ошибка TLS | `Сертификат сервера не доверен` |

Диалоги ошибок не открываются: сообщение уходит в строку статуса панели.

## Тесты

Core проверяется на фейковом сервере `com.sun.net.httpserver.HttpServer`
(по образцу `FakeGitLab`), без сети.

- `GitHubRemote`: `https`, `ssh://`, `git@host:path`, `github.com`,
  GitHub Enterprise с `/api/v3`, вложенный путь, чужой хост.
- Поиск PR по ветке: открытый приоритетнее, пустой список, несколько PR.
- Состояние: черновик, проверки success/failure/pending, пустые check-runs с
  fallback на combined status, приоритет упавших проверок, `mergeable=false`,
  `mergeable=null`, `merged_by` и `merged_at`, закрытый PR.
- Одобрения: `COMMENTED` после `APPROVED` не снимает одобрение,
  `CHANGES_REQUESTED` и `DISMISSED` снимают, недоступный branch protection.
- Создание: тело запроса, заголовок `head` вида `owner:branch`, черновик,
  назначение проверяющего вторым запросом, ошибка назначения не отменяет PR,
  422 «ветка не отправлена» и 422 «PR уже существует».
- Коды 401, 403, 404, 429, 500 и таймаут; токен не уходит на чужой хост:
  панель не создает клиента, если хост настроек не совпал с remote.

UI проверяется без окон: форматирование строки для обоих провайдеров,
параметризованные ключи в русских и английских ресурсах, миграция настроек и
кеша проверяющих.

Ручная проверка в EDT обязательна: форма настроек, создание PR на тестовой
ветке в реальном GitHub, строка состояния и переход в браузер.

## Решения исполнителя

Эти решения приняты без отдельного согласования; их можно отменить, пока не
начата реализация.

- Переименование `GitLabException` в `HostingException` — иначе GitHub-клиент
  бросает исключение с чужим именем.
- Выбор «Тип сервера» в форме настроек — единственный способ поддержать GitHub
  Enterprise на домене без слова `github`.
- Номер в строке для GitHub — `PR-123`, как `MR-123` у GitLab.
- В первой итерации не показываются незакрытые обсуждения и комментарии.
- «Удалить ветку после слияния» показывается только для GitLab.
- Проверяющий для GitHub необязателен; для GitLab сохраняется текущее поведение.
- Настройки хранятся по хосту; старые ключи GitLab читаются как fallback.
- Запросы идут на хост remote; сохраненный адрес сервера — значение по умолчанию.
- `canCreateRequests()` справочный; фактическое право проверяет ответ API.
- Одобрение сохраняется после `COMMENTED`; снимают только `CHANGES_REQUESTED`,
  `DISMISSED` и новые коммиты (GitHub присылает их как `DISMISSED`).
- Приоритет проверок: упали, затем идут, затем прошли; выводы `neutral`,
  `skipped`, `stale` не считаются падением.
- Закрытый PR показывается «Закрыт» без повторного создания из панели.
- Ошибка назначения проверяющего не отменяет создание PR.
- Повторный запрос при пустом `mergeable` не выполняется: обновление по кнопке
  или при следующем показе панели.
- GitHub использует системный прокси; GitLab остается без прокси.
