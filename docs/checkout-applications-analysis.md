# Переключение веток, приложения EDT и снимки состояния

Диагностика к вопросу «плагин переключает ветку, но приложение остается на базе
прежней ветки, а согласование со снимками из 0.17.1 замедляет переключение до
минут».

Все утверждения о EDT ниже проверены по байткоду установленных сборок, а не по
документации. Результаты проверки на рабочем проекте и замеры — в разделе
«Результат проверки на рабочем проекте».

## Стенд

- 1C:EDT 2026.1.3+25, Eclipse 4.30 (Windows), JDK 17 (axiom-jdk 17.0.16),
  JGit 6.8.12.
- Плагин Git Flow 0.17.2 установлен в пользовательскую область конфигурации
  `~/.eclipse/org.eclipse.platform_4.30.0_1902511643_win32_win32_x86_64`;
  записи о бандлах ядра и UI есть в `bundles.info` этой области. В каталоге
  `plugins` самой EDT плагина нет и быть не должно.
- Проект пользователя: репозиторий на 69 080 файлов, 4,4 ГБ, около 90 локальных
  веток, у веток свои файловые базы по префиксам процесса разработки
  (`fix/`, `feat/`, `releases/`, развертывание копией базы).

## Короткий итог

1. Плагин меняет ветку своим путем: stash → JGit checkout → возврат stash →
   `refreshLocal(DEPTH_INFINITE)`. Штатный checkout EDT делает другой набор
   шагов, но **тоже не переключает базы**: в `BranchCheckoutManager` нет ни
   одного обращения к инфобазам.
2. Базу под текущую ветку подставляет отдельный компонент EDT —
   `GitRepositoryAssociationContextManager` из `com._1c.g5.v8.dt.team.git.infobases`.
   Он слушает **события изменения ссылок Git** и **изменения ресурсов
   workspace**, вычисляет контекст ассоциации по имени ветки и уведомляет
   слушателей. Дальше `InfobaseAssociationManager` меняет привязку базы,
   `InfobaseSynchronizationManager` переподключается к базе ветки (в логе это
   задача «Переподключение к <ветка>»), состояние приложений пересчитывается.
3. Значит, переключение приложения не связано со снимками состояния. Снимки —
   кеш производных данных модели, они сокращают переиндексацию, но базу не
   выбирают.
4. Отсюда главная гипотеза: наш checkout не доставляет сигнал об изменении
   ссылок, который ожидает `GitRepositoryAssociationContextManager`. Поэтому
   контекст ассоциации остается прежним, и приложение продолжает работать с
   базой предыдущей ветки.
5. Согласование 0.17.1 было медленным по другой причине: `begin`/`end`
   синхронно создают снимок исходной ветки и восстанавливают снимок целевой под
   эксклюзивной блокировкой модели. На 69 080 файлах это минуты. Кеш тут не
   спасает: ключ кеша — коммит HEAD, после каждого коммита снимок устаревает.

## Как EDT связывает ветку и базу

`GitRepositoryAssociationContextManager` реализует
`IInfobaseAssociationContextProvider`: `get(IProject)` возвращает
`InfobaseAssociationContext` для текущей ветки
(`GitBranchToContextConverter.convert`). Ассоциация базы берется не «на
проект», а «на проект и контекст»: `IInfobaseAssociationManager.getAssociation(
project, context)`.

Вложенный `CheckoutListener`:

* подписан на `IWorkspace.addResourceChangeListener(this, 6)` — типы
  `PRE_DELETE` и `POST_CHANGE`; при них забывает запомненный контекст проекта;
* подписан на список слушателей EGit/JGit
  (`RepositoryCache.INSTANCE.getGlobalListenerList().addRefsChangedListener`);
  на `RefsChangedEvent` для каждого проекта репозитория: вычисляет новый
  контекст, сравнивает с запомненным и, если он изменился, пишет строку в
  трассу и вызывает
  `IInfobaseAssociationContextListener.contextChanged(project, old, new)`.

Получатели `contextChanged` в EDT:

* `InfobaseAssociationManager$ContextChangeListenerForwarder` — меняет
  действующую привязку базы;
* `InfobaseSynchronizationManager$AssociationChangedConnectionHandler` —
  переподключает базу (та самая задача «Переподключение к …»);
* делегаты приложений (`InfobaseApplicationProvisionDelegate`), из которых
  считается состояние обновления приложения.

Ссылки на ассоциации хранятся в
`<workspace>/.metadata/.plugins/com._1c.g5.v8.dt.platform.services.core/<проект>/.references`
(`ProjectSettingsStoreLocationProvider.getStoreBaseLocation` +
`PreferenceFileAssociationReferenceStore`). В рабочей области пользователя этого
каталога нет, то есть по контекстам веток ничего не записано: стоит проверить
это отдельно, потому что переключать можно только то, что привязано.

## Что делает штатный checkout EDT

`com._1c.g5.v8.dt.internal.team.ui.BranchCheckoutManager.checkoutBranch`:

1. `IndexLockUtils.validateRepositoryIndexLock` — предупреждение об `index.lock`;
2. модальный `ProgressMonitorDialogWithTitle`;
3. `synchronizeProjectResources` — ожидание синхронизации проекта;
4. EGit `BranchOperationUI.checkout` — checkout с обновлением ресурсов;
5. `doCheckout` — обход `IBranchCheckoutListener`: `beforeCheckout` → checkout →
   `afterCheckout`;
6. диалог и запись ошибки в лог.

Единственный слушатель в EDT — `CheckoutInterceptor$CheckoutListener` из
`com.e1c.g5.v8.dt.snapshot.integration.ui`: он вызывает
`IGitIntegrationManager.beginManagedCheckout` / `endManagedCheckout`.

Внутри `begin`/`end` (`SnapshotManagementOperation`):

* `begin` → приостановка синхронизации инфобаз → `createSnapshots` (снимок
  состояния, которое покидаем);
* `end` → `restoreSnapshots` (снимок целевой ветки) → `finish` →
  `rebuildStaleRepositoryStateProjects` → возобновление синхронизации инфобаз.

Все это выполняется под `DtExclusiveContext`, который блокирует конвейер
производных данных модели (`DerivedDataManager.blockAsyncPipeline`); в рабочем
логе EDT это видно как `External forced block ... DtExclusiveContext` с трассой
`SnapshotManagementJob.run → SnapshotManagementOperation.prepare →
SnapshotFlow.finishScheduling`.

## Когда создается и когда восстанавливается снимок

`BranchFilteredIntegrationStrategy.computeNecessaryOperations`:

* общий ключ `enabled` по умолчанию **false**, шаблоны веток по умолчанию —
  `master`, `main`, `develop`, плюс префиксы веток процесса разработки с
  развертыванием `copyInfobase`, `restoreInfobase`,
  `restoreInfobaseFromDatabaseFile`;
* CREATE — если для HEAD исходной ветки снимка нет (обычный случай после
  коммита);
* RESTORE — только если снимок для HEAD целевой ветки уже существует;
* при непустом рабочем дереве не делается ничего.

Снимки лежат в
`<workspace>/.metadata/.plugins/com.e1c.g5.v8.dt.snapshot.integration.git/snapshots/<проект>/<sha1>.fzip`.
Асинхронный путь (`SnapshotManagementJob` для checkout, который EDT не
сопровождал) умеет только восстановление, поэтому кеш наполняется только на
managed checkout.

## Что делает плагин 0.17.2

1. stash локальных изменений;
2. `git.checkout().setName(...)` через JGit;
3. возврат stash;
4. `project.refreshLocal(DEPTH_INFINITE)` отдельным Job на проект.

Репозиторий берется через `RepositoryMapping.getMapping(project).getRepository`,
то есть это экземпляр EGit, а не самодельный `FileRepository`. Это важно:
события JGit, отправленные через него, доходят до глобальных слушателей EGit.

Чего нет: проверки `index.lock`, ожидания синхронизации проекта, обновления
ресурсов средствами EGit, уведомления об изменении ссылок, `begin`/`end`,
приостановки и возобновления синхронизации инфобаз.

## JGit 6.8: как уведомить об изменении ссылок

Публичный метод `Repository.notifyRefsChanged()` в 6.8 отсутствует. Есть
`Repository.fireEvent(RepositoryEvent)`: он проставляет источник, рассылает
событие локальным слушателям репозитория и глобальному списку. То есть
`repository.fireEvent(new RefsChangedEvent())` — штатный способ сообщить
EGit и EDT, что ссылки изменились, если наш путь их не порождает.

`RefsChangedEvent` не привязан к конкретным ссылкам, поэтому EDT пересчитает
контекст для всех проектов репозитория — это именно то, что нужно после
переключения ветки.

## Почему 0.17.1 был медленным

| Этап | Источник | Порядок |
|---|---|---|
| Ожидание сервиса | `EdtCheckoutSupport`, до 10 с | секунды |
| `prepare` | ожидание готовности проектов | до 15 с |
| CREATE снимка исходной ветки | `begin` → `createSnapshots` | десятки секунд — минуты |
| RESTORE снимка целевой ветки | `end` → `restoreSnapshots` | десятки секунд — минуты |
| Блокировка модели и пересчет после restore | `DtExclusiveContext` | десятки секунд — минуты |
| Наш `refreshLocal(DEPTH_INFINITE)` | `ProjectRefreshSupport` | секунды |

Пользователь оценил 0.17.1 в 1–3 минуты против 10 секунд у 0.17.2. Это
согласуется: доминируют CREATE и RESTORE. Добавление кеша не поможет, потому
что снимок привязан к коммиту: после коммита HEAD новый, снимка нет, и
следующее переключение снова создает его.

## Что проверить (минимальные опыты)

Опыт 1 — эталон EDT. Переключить ветку штатно (панель Git → Checkout) и
посмотреть, меняется ли база/приложение и появляется ли задача «Переподключение
к …». Это ответ на вопрос, что именно EDT делает в этой конфигурации без
плагина.

Опыт 2 — доходит ли сигнал от плагина. Включить трассировку
(`com._1c.g5.v8.dt.team.git.infobases`: `debug`, `trace`; при необходимости
`com.e1c.g5.v8.dt.snapshot.integration.git`: `debug`, `trace`), переключить
ветку плагином и найти в `<workspace>/.metadata/trace.log` строку о смене
контекста ассоциации. Нет строки — сигнал не доходит, гипотеза подтверждена.

Обе трассы пишутся в `<workspace>/.metadata/trace.log` с миллисекундными
таймстампами; файл опций — `.options` в каталоге установки EDT, туда же можно
дописать ключи.

## Что и где править

1. **Сигнал о смене ветки.** После успешного checkout и возврата stash
   отправить `repository.fireEvent(new RefsChangedEvent())`. Одна строка в
   пути checkout, публичный API JGit, без внутренних классов EDT. Ожидаемый
   эффект: EDT сам переключит контекст ассоциации и переподключит базу ветки.
   Проверять опытом 2.
2. **Снимки не трогать в основном пути.** Оставить 0.17.2-поведение: снимки
   EDT применяет сама асинхронно, если сочтет нужным. Если понадобится
   ускорение переиндексации, добавлять отдельный режим: только RESTORE при
   готовом `.fzip`, создание снимка — фоном, не в пути переключения.
3. **Обновление ресурсов.** `refreshLocal(DEPTH_INFINITE)` на 69 080 файлов —
   лишняя работа, если событие изменения ссылок заставит EGit обновить
   проекты. Проверить после шага 1 и, если EGit справляется, заменить полный
   обход на точечное обновление. Выполнено в 0.17.4, см. ниже.
4. **Проверка `index.lock` и ожидание синхронизации** — дешевые страховки из
   штатного пути, которые стоит перенести в плагин, если шаг 1 не сработает.

## Результат проверки на рабочем проекте

09.11.2026 собрана диагностическая сборка 0.17.3 (журнал
`<workspace>/.metadata/gitflow-diagnostics.log`), выполнены два переключения
плагином: `feat/npo-861-checked-documents` → `master` и обратно.

Главное: гипотеза о потерянном сигнале **не подтвердилась**. JGit при нашем
checkout сам порождает `RefsChangedEvent`, EDT его получает и меняет контекст
ассоциации:

```
13:32:13.165 событие ссылок: наш репозиторий, ветка=master
13:32:13.388 контекст изменен: P/bp3, было=refs/heads/feat/npo-861-checked-documents,
             стало=refs/heads/master
13:33:19.492 контекст изменен: было=refs/heads/master,
             стало=refs/heads/feat/npo-861-checked-documents
```

Отправка события вручную («fallback») не потребовалась ни разу.

Причина того, что база не переключалась, видна в состоянии сразу после
переключения на `master`:

```
13:32:14.878 контекст ассоциации: InfobaseAssociationContext[refs/heads/master]
13:32:14.878 ассоциация по текущему контексту: нет
13:32:14.878 ассоциация по контексту ветки: нет
```

Привязки баз хранятся по контекстам в
`<workspace>/.metadata/.plugins/org.eclipse.core.resources/.projects/<проект>/com._1c.g5.v8.dt.platform.services.core/refs/heads/<ветка>/AssociationData.properties`.
Файл для `master` содержит пустой список баз:

```
Infobases=
DefaultInfobase=625d0691-f889-42b9-8055-23ae0971126f
```

То есть у контекста `master` нет ни одной привязанной базы, поэтому EDT нечего
переключать: `getAssociation(project, master)` возвращает пусто, состояние
равенства не считается. У веток `feat/*` и `fix/*` привязки корректные
(например, `feat/npo-861-checked-documents` → база `61e3c342…`).

База `625d0691…` при этом существует и используется приложением автономного
сервера «ЕДТ БНКО - Основной» (модуль
`com.e1c.g5.v8.dt.platform.standaloneserver.infobase`), но к контексту `master`
она не привязана.

Замеры переключений (эта сборка не вызывает согласование со снимками):
переключение на `master` — 5,7 с, обратно на ветку — 13,1 с, обновление проекта
— 3,8–4,0 с на каждое.

## Проверка ручной привязки базы к `master`

В `refs/heads/master/AssociationData.properties` вручную записана база
`625d0691…` (с предварительной копией файла). После запуска EDT:

* у контекста `master` появилась привязанная база;
* в панели «Приложения» появилась вторая запись — разрабатываемое приложение
  проекта на базе автономного сервера, при запуске стало нужно выбирать между
  автономным сервером и приложением;
* при переключении ветки на `master` EDT попытался переподключить базу и упал:

```
java.lang.IllegalArgumentException: Infobase ЕДТ БНКО - Основной is already connected
```

Вывод: разрабатываемое приложение в EDT — это пара «проект + база»,
зафиксированная в привязке контекста ветки. База автономного сервера занята
самим сервером, поэтому привязать ее к проекту нельзя: получается дубль
приложения и конфликт подключения. Ручная привязка откачена, файл возвращен к
исходному виду.

## Вывод

Переключение ветки плагином и переключение базы в EDT согласованы: сигнал о
смене ссылок доходит, контекст ассоциации меняется, EDT переподключает базу,
если она привязана. Править путь checkout не нужно.

Для ветки `master` привязка не нужна: там работает приложение на автономном
сервере, чья база не может быть привязана к проекту (см. выше). Это ограничение
штатного поведения EDT, а не плагина, и в Git Flow его исправлять не нужно.

## Открытые вопросы

* Обращение в поддержку 1С: приложение на локальном автономном сервере не
  создает привязку базы к проекту (нет `behaviourDelegate`), а ручная привязка
  приводит к дублю приложения и ошибке `is already connected`.

## После 0.17.4

* Точечное обновление реализовано: `BranchOperations.checkout` возвращает пути
  измененных файлов (`ChangedPaths`), а `ProjectRefreshSupport` обновляет
  только их каталоги. Полный обход проекта остается запасным вариантом, если
  список путей пуст или в нем больше 4096 каталогов.
* «Требуется обновить» после возврата на ветку — это отставание базы, а не
  свойство переключения. Пример: база ветки отставала на два объекта из
  коммита 13:30, и EDT догрузила их только при возврате в 14:43.
* Приложение на автономном сервере показывает «требуется инкрементальная
  загрузка», пока открыта модель другой ветки: его база хранит состояние
  `master`. Обновлять его из ветки нельзя — в базу `master` уедет конфигурация
  ветки.
* После синхронизации обеих баз переход ветка → `master` → ветка не вызвал ни
  одной загрузки: проверено по журналу загрузок EDT 09.11.2026.
